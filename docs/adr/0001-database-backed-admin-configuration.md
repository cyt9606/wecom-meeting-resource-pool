# ADR 0001：数据库驱动的管理员与高级资源配置

- 状态：已接受
- 日期：2026-07-28

## 背景

应用最初从环境变量读取管理员和高级会议资源。该方式适合首次部署，但任何调整都需要登录服务器、修改配置并重启服务，无法满足由业务管理员在前端即时维护资源池和管理权限的需求。

系统面向企业全员，但管理操作频率低。管理员权限撤销应立即生效，高级资源还会被历史预约记录引用，因此配置变更需要兼顾权限安全和数据可追溯性。

## 决策

1. 使用现有 PostgreSQL 保存管理员名单和高级资源配置。
2. 每个受保护请求都从数据库判断管理员身份，不缓存角色，以保证新增或撤销立即生效。
3. `WECOM_ADMIN_USERIDS` 只在管理员表为空时执行首次引导；数据库中已有管理员后，重启不会覆盖后台配置。
4. 新增管理员和高级资源前，通过企业微信通讯录接口校验 userid。
5. 删除管理员时锁定管理员记录，并强制至少保留一名管理员。
6. 高级资源不做物理删除，只允许编辑和启停，以保留预约外键与审计历史。
7. 所有配置变更写入现有操作日志。

## 影响

- 管理员可在前端完成日常配置，修改即时生效且无需重启。
- 每个鉴权请求增加一次轻量数据库查询；基于当前内部系统低并发场景，该开销可接受。
- 环境变量不再是管理员配置的持续事实来源，但仍是新环境首次启动的恢复入口。
- 资源停用后不再参与新会议调度，既有预约与统计仍可查询。

## 备选方案

- 继续使用环境变量：实现简单，但无法在线配置，也无法即时撤销权限。
- 将角色写入登录会话：请求更快，但撤销权限要等会话过期，不符合即时生效要求。
- 物理删除资源：界面直观，但会破坏历史引用或迫使复杂的数据迁移，因此不采用。
